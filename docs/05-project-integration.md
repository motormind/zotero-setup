# 5. Using it in research projects

## Installation – three ways

| Way | Command | When |
|---|---|---|
| **Global tool** (recommended) | `uv tool install git+https://github.com/motormind/zotero-setup`<br>or `pipx install git+https://github.com/motormind/zotero-setup` | one `zt` for all projects; update: `uv tool upgrade zotero-setup` |
| **Dev dependency** | `uv add --dev "zotero-setup @ git+https://github.com/motormind/zotero-setup@v0.1.0"` → `uv run zt …` | pin a version per project; CI uses the same version |
| **Git submodule** | `git submodule add https://github.com/motormind/zotero-setup tools/zotero-setup` → `python3 tools/zotero-setup/zt.py …` | no install; docs travel with the project |

## Recommended layout

```
my-project/
├── .zotero.toml        # committed: group ID, collection, paths – NO secrets
├── .env                # NOT committed: ZOTERO_API_KEY
├── .env.example        # committed: placeholders
├── .mcp.json           # optional, committed: only ${VAR} references
├── references.bib      # generated by `zt pull`
└── papers/
    ├── ids.txt         # DOIs / arXiv IDs, one per line, # for comments
    ├── extra.bib       # optional: your own BibTeX entries to push
    └── *.pdf           # optional: <citekey>.pdf / <doi>.pdf / <arxiv-id>.pdf
```

Whether PDFs belong in git is a per-project decision (copyright, repo size). In public repos: do **not** commit publisher PDFs – add `papers/*.pdf` to `.gitignore` and share them via Zotero only.

PDF file names: special characters and case are ignored, so `10.1038/nature14539` matches `10.1038_nature14539.pdf` or `101038nature14539.pdf`.

## Groups & collections

- One group per team/lab/program, with **one collection per project** inside it (sub-collections are fine).
- `zt collections` lists keys and paths; put the key into `.zotero.toml` → `collection`.
- `zt pull` exports the top-level items of **that** collection only (not its sub-collections).
- Tags like `src:<project>` (via `tags` in `.zotero.toml`) show where an entry came from.

## Typical workflows

```bash
# found a paper → add it
echo "https://arxiv.org/abs/2005.14165  # GPT-3" >> papers/ids.txt
zt push -n && zt push && zt pull
git add papers/ids.txt references.bib && git commit -m "add GPT-3 paper"

# a colleague added papers in Zotero → refresh the bibliography
zt pull && git diff references.bib

# move an old project's .bib into the group
zt push -n   # with bib_files = ["old/literature.bib"]
```

## LaTeX / Quarto / Pandoc

```latex
\usepackage[backend=biber]{biblatex}
\addbibresource{references.bib}
```

```yaml
# Quarto / Pandoc
bibliography: references.bib
```

About citekeys: the Web API generates keys like `lecun_deep_2015`. If you need stable, self-chosen keys, use [Better BibTeX](https://retorque.re/zotero-better-bibtex/) with auto-export in Zotero desktop – `zt push` writes `Citation Key: …` into *Extra*, which Better BibTeX picks up. When using `zt pull`, take the keys from `references.bib`.

## CI (GitHub Actions) – keep `references.bib` up to date

```yaml
# .github/workflows/references.yml
name: references
on:
  workflow_dispatch:
  schedule: [{ cron: "0 5 * * 1" }]   # Mondays
permissions:
  contents: write
jobs:
  pull:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install git+https://github.com/motormind/zotero-setup@v0.1.0
      - run: zt pull
        env:
          ZOTERO_API_KEY: ${{ secrets.ZOTERO_API_KEY }}   # read-only key!
      - run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add references.bib
          git diff --cached --quiet || git commit -m "chore: update references.bib" && git push
```

Always use a separate **read-only** key limited to this group for CI.
